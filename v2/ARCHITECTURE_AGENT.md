# Hugind – Agent Runtime Architecture Overview

## 1. Purpose

Hugind is a **host-orchestrated execution platform** for running **untrusted JavaScript agents** safely, composing them into workflows, and exposing model-backed functionality via CLI, server APIs, and future desktop/web applications.

Core goals:

* Run **untrusted, possibly LLM-generated code** safely
* Keep agents **unaware of each other**
* Centralize orchestration and permissions in the **host**
* Avoid duplicated logic across CLI, server, and UI
* Ship as a **single binary** where possible

---

## 2. High-level architecture

Hugind is split into three conceptual layers:

```
┌──────────────────────────┐
│        Interfaces        │
│  CLI · HTTP · Desktop    │
└──────────┬───────────────┘
           │
┌──────────▼───────────────┐
│        Core APIs          │
│  config · model · runtime│
└──────────┬───────────────┘
           │
┌──────────▼───────────────┐
│   JS Sandbox Runtime     │
│   (QuickJS via Rust)     │
└──────────────────────────┘
```

* **Interfaces** are thin adapters (CLI, HTTP server, etc.)
* **Core** contains all reusable logic
* **JS runtime** is a strict sandbox for untrusted agents

## 3. Source layout (`src/`)

```
src/
├── main.rs                 # CLI entrypoint (thin)
├── cli/                     # CLI subcommands only
│   ├── args.rs
│   ├── agent.rs
│   ├── model.rs
│   ├── config.rs
│   └── chat.rs
│
├── core/                    # reusable business logic
│   ├── js/                  # JS sandbox runtime
│   │   ├── runtime.rs
│   │   ├── loader.rs
│   │   └── globals.rs
│   ├── config/
│   ├── model/
│   ├── runtime/
│   └── errors.rs
│
├── server/                  # HTTP/OpenAI-compatible server
│   ├── http.rs
│   ├── openai.rs
│   └── state.rs
│
└── shared/                  # cross-cutting utilities
    ├── paths.rs
    ├── logging.rs
    └── types.rs
```

**Rule:**
If logic is needed by more than one interface (CLI, server, UI), it belongs in `core/` — not in `cli/` or `server/`.

## 4. JavaScript execution model

### 4.1 JS is untrusted

All JavaScript code is considered **untrusted**:

* written by users
* generated by LLMs
* downloaded from the internet

Therefore:

* JS runs inside a **QuickJS sandbox**
* JS has **no access** to:

  * filesystem
  * network
  * shell
  * native FFI
* JS can only do what the host explicitly exposes

---

### 4.2 JS sandbox implementation

Located in `core/js/`.

#### `loader.rs`

* Enforces **local-only ES module imports**
* Allows only `./` and `../`
* Prevents directory escape
* Blocks npm, URLs, native modules

This is the **import security boundary**.

#### `globals.rs`

* Defines the **capabilities exposed to JS**
* Currently minimal (`print`)
* Future additions go here (logging, emit, tools)

This is the **capability boundary**.

#### `runtime.rs`

* Creates QuickJS `Runtime` + `Context`
* Installs loader and globals
* Executes a single JS entry module

This file:

* does **not** know about workflows
* does **not** know about CLI or HTTP
* only runs *one agent*

---

## 5. Agent contract

Agents are **pure workers**.

They do not:

* know about other agents
* know about workflows
* invoke other agents
* control execution order

### Canonical agent shape

```js
export default async function main(ctx, input) {
  // input: JSON from host
  // ctx: limited capabilities

  return output; // JSON
}
```

Agents may:

* compute
* transform data
* call allowed tools (future)

Agents may:

* log for humans

Agents **do not orchestrate**.

---

## 6. Host orchestration model

The **host (Rust)** is the only component that:

* decides which agent runs
* passes output of one agent as input to another
* manages workflows
* enforces permissions
* handles retries, timeouts, failures

Agents are unaware they are part of a workflow.

This prevents:

* privilege escalation
* agent-to-agent coupling
* hidden control flows

---

## 7. CLI design philosophy

The CLI (`hugind`) is a **thin adapter**, not a logic layer.

Example commands:

* `hugind model …`
* `hugind config …`
* `hugind server …`
* `hugind agent run …`
* `hugind chat …`

Rules:

* CLI parses arguments
* CLI calls `core` APIs
* CLI never reimplements logic

All CLI subcommands should be replaceable by:

* HTTP APIs
* desktop apps
* scripts

---

## 8. Configuration model

Configuration is centralized in `core/config/`.

* Parsed once
* Validated once
* Shared by:

  * CLI
  * server
  * UI
  * tests

There must never be:

* separate YAML parsers per subcommand
* duplicated config logic

---

## 9. Server model

The HTTP server:

* depends on `core`
* exposes APIs (e.g. OpenAI-compatible)
* does not own model/runtime logic

The server is **just another interface**, like the CLI.

---

## 10. Design constraints (intentional)

Hugind intentionally avoids:

* agent-to-agent calls
* shared mutable global state
* dynamic native module loading
* unrestricted JS APIs
* tight coupling between CLI and runtime

These constraints exist to:

* support untrusted code
* support LLM-generated code
* keep the system auditable
* keep security boundaries obvious

---

## 11. Guiding principle

> **Agents compute.
> The host decides.
> Interfaces adapt.**

If a feature breaks this principle, it is likely incorrect.
